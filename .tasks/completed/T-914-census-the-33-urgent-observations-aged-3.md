# T-914: Census the 33 urgent observations aged 31-90 days: what is already fixed, superseded, duplicated, or still live

## Context

**RESCOPED 2026-09-28, before any work: the census already exists, and doing it again was the wrong
task.** Filed to census the 33 urgent observations aged 31–90 days. Four commands in, every one of
those 33 turned out to be enumerated, classified and reasoned about in two committed reports —
`docs/reports/T-702-urgent-named.md` and `docs/reports/T-703-inbox-residue.md`, both generated by
`tools/_t703-inbox-residue.py --write` on 2026-09-20, both explicitly marked *"regenerate, do not
hand-edit"*.

So this would have been the **third** census of the same queue. That is the finding, not a
side-note: **analysis is not the bottleneck.** The queue has been measured repeatedly and drained
never.

|---|---|

| carried-by-active-task | 20 |

| dangling-task | 1 |

And its reason column names the blocker outright, on 82 rows:

> *"T-NNN is work-completed; thread lives in `.context/episodic/T-NNN.yaml` — **closure blocked:
> dismiss verb cannot record where the content lives**"*

### The actual bottleneck

`fw note` has five verbs: `list`, `count`, `triage`, `promote`, `dismiss`. **There is no `resolve`.**

- `dismiss` means *"not worth doing"*. For 82 items that were **already done**, that is the wrong
  statement — dismissing them would record a decision nobody made and lose the pointer to where the
  work landed.
- `promote` is wrong too: these do not need a task, they had one.
- So the only honest disposition has no verb, and the items stay `pending` forever. Not through
  neglect — through **an unrepresentable state**.

The proof that the state is wanted: **three observations already carry `status: resolved`**
(OBS-313, OBS-318, OBS-331), set by hand, with no field recording the carrier. The status exists in
the data and has no verb and no schema behind it.

**This is why the queue grows monotonically.** Every session adds observations; 82 of them cannot
leave; the urgent count climbs; and at 39% urgent the flag stops meaning anything — the same
false-signal class this project keeps finding everywhere else.

# THE DEFAULT — redirect to a file, then grep the file:
#     cmd > /tmp/.out 2>&1 && grep -q "PATTERN" /tmp/.out
#     curl -sf "$(bin/fw watchtower url)/page" -o /tmp/.out && grep -q "PAT" /tmp/.out
# Correct at any output size, and `&&` keeps the PRODUCING command's exit code in
# the verdict. Reach for this first; the alternative below is the special case.
#
# Why not `cmd | grep -q PAT` (L-387): P-011 runs each line with PIPEFAIL LIVE
# (errexit is not — see below). When grep matches it exits and closes stdin while cmd is still
# writing, cmd takes SIGPIPE, the pipeline exits 141 — verification "fails" with
# the pattern present. Captured 4× (T-1716, T-1838, T-1862, T-1863).
#
# THE EXCEPTION — capture first, grep the capture:
#     out=$(cmd 2>&1); echo "$out" | grep -q "PATTERN"
# Valid ONLY while "$out" fits the 65536-byte pipe buffer, and it is on you to
# know that it does. Above that the form inverts and becomes the very failure
# L-387 describes: echo blocks on the full pipe, grep -q exits, echo takes
# SIGPIPE, rc=141 (T-2743 — measured on a 146,366-byte Watchtower page, 3/3 runs,
# deterministic not racy; rendered routes run 50-200KB, so anything that curls a
# page is over the line). It also discards cmd's exit code, so a 404 yields an
# empty capture that grep merely fails to match rather than a failed line.
# If you do use it: single pipe only, no intermediate tail/awk/sed stage between
# capture and grep (T-2090) — the middle stage is what `grep -q` slams its stdin
# on, and grep scans the whole captured string anyway, so the `tail -3` was
# cosmetic. `echo "$out" | grep -q PAT`, nothing between.
#

# to `grep -qE "[0-9]+ passed"` matches the same output. Keep the exit code:
#     python3 -m pytest <file> -q > /tmp/.out 2>&1 && grep -q passed /tmp/.out

#     out=$(python3 -m pytest <file> -q 2>&1); echo "$out" | grep -q passed && ! echo "$out" | grep -q failed
