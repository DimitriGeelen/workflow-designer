# T-567: Episodic generator emits git subjects as double-quoted YAML, so a backslash in a commit message makes the episodic unparseable

## Context

Completing T-562 generated `.context/episodic/T-562.yaml`, and the file does not parse:

```
yaml.scanner.ScannerError: while scanning a double-quoted scalar
  in ".context/episodic/T-562.yaml", line 61, column 13
found unknown escape character '-'
```

The generator mines `git log` and writes each subject into the `git_timeline:` block as a
**double-quoted** YAML scalar. YAML permits only a fixed escape set inside double quotes
(`\n \t \" \\ \/ \0 \xNN \uNNNN` …). T-562's commit message quotes the sanitizer regex
`/[^a-z0-9_\-]/g`, so the file contains a literal `\-`, which is not in that set.

**Any commit message containing a backslash before a non-escape character produces an
unparseable episodic.** That is not a property of this commit; it is a property of every
commit that quotes a regex, a Windows path, or an escaped shell character — routine
content for a project whose commit messages carry evidence.

The failure is loud at generation time and silent afterwards: the task still completed,
moved to `completed/`, and the file was written. What is lost is the episodic memory of a
finished task — one of the three memory types — for any consumer that parses YAML.

The framework's own error text says: *"This is a generator bug; do not edit the output by
hand. Capture the source task and report on framework:pickup with
msg_type=pickup-bug-report."* Both halves are honoured: the fix is in the generator, the
output is regenerated rather than patched, and the report goes upstream.

**Symptom:** `fw task update T-562 --status work-completed` printed a Python traceback —
`yaml.scanner.ScannerError … found unknown escape character '-'` — after the task had
already passed every gate. The task completed anyway: it moved to `completed/`, and the
episodic file was written. Only its content was lost.

**Root cause:** `agents/context/lib/episodic.sh:367-369` wrote git subjects into a
**double-quoted** YAML scalar, escaping `"` and nothing else. A double-quoted YAML scalar
interprets a fixed escape set, so any backslash before a character outside that set makes
the file unparseable. T-562's commit message quotes `/[^a-z0-9_\-]/g`; T-431's quoted a
regex alternation, yielding `\|`.

**Why structurally allowed:** two distinct omissions, and the second is the expensive one.

1. *The correct form was already in the same file.* The `challenges` and `artifacts`
   emitters, two blocks below, mine the **same** `git log --format=%s` subjects and have
   always used single-quoted YAML with `''` doubling. In T-562's own episodic the
   offending message sits **safely** in `challenges` at line 37 while line 61 kills the
   file — identical bytes, two quoting styles, one wrong. Nothing required the three
   emitters of one data source to agree, which is the same shape as T-562's own defect
   (three sanitizers, one validator, no tie) one day apart in a different file.
2. *Nothing ever reads episodic memory back.* The ScannerError is raised once, at
   generation time, to whoever is watching that terminal. Afterwards no instrument in this
   project parses `.context/episodic/*.yaml` — the audit's YAML check covers a small set of
   project files and excludes the 488 episodics. So T-431 sat unreadable for **nine days**
   and was cited as ordinary completed work throughout.

**Prevention:** the emission now matches its siblings, and
`tools/_t567-episodic-yaml-safety-teeth.sh` pins the property that matters — a subject
containing `\-`, `\|`, quotes, apostrophes, colon-space and a trailing backslash must come
back **byte-equal** through the real generator, not merely parse. Two mutants: reverting to
double-quoting must fail, and emitting an empty action must also fail, because "it parses"
is exactly what deleting the content produces. Wired into `tests/run-bridge-tests.sh`.

The *blindness* is deliberately not claimed as fixed. Registered as **G-040**, which closes
only when a routine unattended instrument (the cron audit, or equivalent) parses every
episodic — explicitly not on this repair, and explicitly not on the suite leg, since the
suite runs when someone runs it, which is the condition that already failed.
