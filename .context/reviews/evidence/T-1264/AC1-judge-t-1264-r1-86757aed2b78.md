## Truth of the sentence: NOT met
The AC requires the sentence to be "true to what a save does (a node the import moved back into its lane is redrawn)". It is not.
captureImportedDi runs AFTER lane reconciliation and records `at: [n.x, n.y]` = the reconciled position, so keptShapeXml/keptEdgeXml
treat a reconcile-moved node as unmoved. (The code comment "a node the reconcile moved counts as moved" is not what the code does.)

Concrete, from the committed kitchen-sink golden (the 6 nodes the notice reports as moved back are la2_gw_gateway, la2_3/6/8/10_activity, la2_link_event, file y≈1412–1475 → saved y≈1237–1251):
- la2_gw_gateway (file Gateway_0238ieb, y 1475 → 1245.5, moved by the import): saved as `id="Gateway_0238ieb_di" ... isMarkerVisible="true"`, width 50 — the file's DI id, attribute and size KEPT. Before this change (HEAD~2 golden) it was redrawn: `BPMNShape_la2_gw_gateway`, 48x48.
- la2_6_activity (Activity_0pfhghz, y 1460 → 1237.5): saved `Activity_0pfhghz_di`, 100x80 (file's) instead of the designer's 110x64.
- flow_2 (Flow_0a4nevl, gateway → la2_6_activity): saved with the file's ORIGINAL waypoints 788,1500 → 920,1500, while both its end shapes now sit at y 1237.5–1317.5. The saved line runs ~200px below the shapes it connects. flow_3 likewise (1020,1500 → 1160,1500).
So on save, shapes the import moved keep this file's sizes/ids and the lines between them keep their (now detached) bends — the opposite of what the notice says. The browser harness _t1264 does not catch this: its setup asserts the import moved nothing ("the test cannot bite").

(Aside: some kitchen-sink start/end events appear to swap DI ids between fixture and golden; that is the duplicate-display-id defect already filed as T-1332, not counted here.)
