### Step 2b: Typing from the definition holds against the evidence
- The finding is confirmed. Without `aef:eventDef`, an intermediate catch/throw decodes to linkEventCatch/Throw, so a
  third-party timer was shown as a link. That is the reason part 2 exists.
- src:13547-13550 types the event only when all of these hold: no aef:eventDef, no link definition, a catch host
  (`_catchHost`: intermediateCatchEvent / boundaryEvent, src:13530), and exactly one native definition whose kind the
  designer models (EVENT_KIND_TYPE: timer, message, error). Start and throw hosts stay untyped. Typed events export as
  intermediateCatchEvent, so typing them would flip the tag (T-237); scoping them out is correct.
- The no-added-`aef:eventDef` promise: src:12196 omits `<aef:eventDef>` for a node with native definitions while the
  binding is empty, and writes it once a binding is set. An unedited open-and-save is therefore byte-faithful, and a
  binding edit is never lost. Sound.
- Requiring exactly one definition is right. An event with several definitions is a BPMN "multiple" event, and the
  designer has no type for it, so leaving it plain is correct.

### Step 3: Ruling on the open question
**Ruling: a plain catch/throw rendering, not a new generic type.** This applies to signal, escalation, conditional,
compensate, cancel and terminate (and to any throw or start host).
Why:
- A new type would add vocabulary with nothing behind it. The designer has no binding, no runtime and no `aef:eventDef`
  kind for these definitions. The type would carry a name and nothing else. It would also need export, import and
  palette entries and IW-1 vocabulary review for no functional gain.
- The plain rendering reuses an existing concept: the T-308 bare catch event (src:4115, double ring, muted palette,
  "an event of unspecified kind"). It adds only a throw variant (src:4131) and a boundary ring. The original tag and the
  verbatim definition stay in the file, so nothing is lost and the semantics stay with the document. The designer does
  not claim to understand them.
- It removes the actual defect, the link semantics (chevron, handoff reading) on events that are not links:
  `isPlainEvent` requires that there is no linkDef.
- A typed glyph per kind (signal triangle, escalation arrow) can be added later as a rendering-only step, without
  changing the model. A new type, by contrast, would be hard to take back once maps were saved with it.

### Observations (not blocking, outside the shape)
- A plain event is still node type linkEventCatch/Throw. If the properties panel still offers link fields for it, a user
  could give it a link target, and the export would then carry `aef:link` beside, for example, a signal definition.
  This is worth a later check or a guard, but it is a UI follow-up, not a flaw in the shape.
- The prototype's open item (2), source indentation of nested children, is cosmetic. It is not addressed in Decisions.
  It does not affect validity.

Conclusion: both parts hold against the evidence and the code built from them. The open question is ruled: plain
catch/throw. Green.
