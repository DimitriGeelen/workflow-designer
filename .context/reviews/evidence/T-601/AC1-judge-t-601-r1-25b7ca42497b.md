## Findings
### F1: the default map still has a label on the lane header strip (fails the first Expected clause)
On a fresh load of the default document, start event **"Investigation requested"**
(lane **Framework · Authority**) renders its name at bbox x=81..197 and its id badge
`frw_1_investigation` at x=85..191. The lane header strip ends at x=90, so both lines sit
about 5-9px on the grey header strip. Screenshot: `rev-default-map.png` (the "I" of
"Investigation" sits on the header strip). The label overlaps only the header strip of its
own lane. It does not reach into a neighbouring lane.

Cause, measured: scDefault=3, scRight=3, scLeft=4. Right is not *strictly* better, so the
"ties keep the default" rule (`src/aef-workflow-designer.html`, the fallback at the end of
`adjustLabelPlacements`) restores the below placement, which is on the header. The
in-band clamp in `place()` only applies to side placements. The default below placement is
never shifted clear of the strip. The scorer sees the header overlap and the pass still
leaves the label there.

The AC's escape clause ("labels with nowhere clean to go sit below their shape as before")
does not cover this. The first clause, "No label overlaps the lane header strip", is
unconditional. A horizontal nudge of the below block (as the side placement already gets in
y) would have a clean place to go.

### F2: the operator's reported case is fixed, with a readability cost
`t601-after.png` matches the committed `.context/working/t601-after.png`. The long label is
right of the circle, clear of the header strip, inside the Human · Sovereignty band, with
the badge above the divider. Compared with `.context/working/t600-wrap-on.png` /
`t600-wrap-off.png`, where the label ran across the header and out of the pool, this is clearly
better for lane attribution. However, the outgoing connector now runs through the text
block (horizontally under the 2nd line, then down through the badge column). The task
itself records this as a trade. On this one case I judge it acceptable, because
mis-attributing a lane is worse. It is still a real loss of legibility.

### F3: the task's own self-test no longer passes at this revision
`node tools/_t601-lane-boundary.mjs --self-test` → exit 2:
`SELF-TEST FAIL — L2 passed without the pool term; they assert nothing`.
Under the poison arm, L1 and L3 fail as designed but L2 (divider) stays green. The divider
leg therefore no longer proves anything. That is the guarantee behind "does not extend into
a neighbouring lane". Relatedly, `poolPenalty()` scores each text LINE separately and only
penalises a single line that crosses a divider. A multi-line block split across a divider,
or a block sitting wholly in the next lane, scores zero from the divider term. My lane-bottom
probe (`rev-lane-bottom.png`) did not show a violation, because the node was side-placed
cleanly. Divider containment therefore rests on luck in that scenario, not on a failable leg.

### Lane bands audited (default map)
Human · Sovereignty 62-192 · Framework · Authority 192-322 · Agent · Initiative 322-642.
No label line in the default map extends outside its own lane. The only violation is F1
(header strip).

## What is needed
- Make the below/default placement clear the lane header strip, for example by shifting the
  block right to `POOL_X + LANE_HEADER` when its left edge would land on the strip. The
  alternative is to stop letting a tie restore a placement that is itself on the header.
  Then add a leg that loads the DEFAULT map and asserts no event/gateway label line has
  x1 < POOL_X + LANE_HEADER.
- Repair the L2 divider leg so it fails under the poison arm. Consider scoring the label
  block as a whole against the node's own band, not line by line.
- After that, re-review the readability trade (F2) on a real corpus map.
